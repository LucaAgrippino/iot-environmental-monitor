# IoT Environmental Monitoring Gateway

[![CI](https://github.com/LucaAgrippino/iot-environmental-monitor/actions/workflows/ci.yml/badge.svg)](https://github.com/LucaAgrippino/iot-environmental-monitor/actions/workflows/ci.yml)

**Project status:** Phase 4 (Implementation) in progress. HLD baseline at `hld-v1.0`. LLD baseline at `lld-v1.0`.

A dual-node embedded system demonstrating industrial IoT architecture: a field device collects sensor data and communicates with a gateway via **Modbus RTU**, which then publishes to the cloud via **WiFi/MQTT**.

The author's contributions:

  produced. Generated outputs that contradicted the intended design were rejected or revised.
- Review and validation of every generated document and module.
- Hardware debugging: each module contains a deliberate bug introduced during code generation;
  the author located and fixed each one using a debugger and the design documentation.
- V-Model traceability maintenance — requirements to architecture to design to implementation
  to test.

This workflow reflects a deliberate choice: the author has five years of embedded systems
experience working with established frameworks and company-provided middleware, but had not
previously built a complete embedded system from scratch. This project was undertaken to gain
direct exposure to the full development lifecycle — requirements, architecture, driver
implementation, protocol integration, and cloud connectivity — within a single codebase.
AI generation accelerated the mechanical production; architectural accountability and
hardware validation remained with the author throughout.

## System Overview

| Node | Board | Role |
|------|-------|------|
| Field Device | STM32F469 Discovery | Sensor acquisition, LCD display, Modbus RTU slave |
| IoT Gateway | B-L475E-IOT01A | Modbus RTU master, data aggregation, MQTT to AWS IoT Core |

## Technology Stack

- **Language:** C (OOP-in-C patterns)
- **RTOS:** FreeRTOS
- **Protocols:** Modbus RTU (UART), MQTT (WiFi)
- **Cloud:** AWS IoT Core
- **Hardware Abstraction:** CMSIS register-level drivers; no STM32 HAL above the driver layer
- **Coding Standard:** BARR-C:2018 (subset — see [docs/coding-standard.md](docs/coding-standard.md))
- **Testing:** Unity + CMock via Ceedling

## Layer Scope and Priority

The implementation covers seven functional layers. Layers 1–5 are non-negotiable; Layers 6–7 are good-to-have.

| Layer | Name | Priority |
|-------|------|----------|
| 1 | Sensor Acquisition | Non-negotiable |
| 2 | Processing / State Machines | Non-negotiable |
| 3 | Modbus RTU | Non-negotiable |
| 4 | LCD | Non-negotiable (currently parked — see note below) |
| 5 | WiFi / MQTT | Non-negotiable |
| 6 | Bootloader OTA | Good-to-have |
| 7 | CI/CD extensions beyond bootstrap | Good-to-have |

If timeline pressure requires cuts, the cut order is: Layer 7 extras first, then Layer 6, then
Layer-5 polish (TLS cert rotation, advanced exception flows). The functional core of Layers 1–5
ships regardless.

Layer 4 (LCD) is currently **parked**. The display stack was built and then removed from the
tree during the post-GUI clean restart; the full snapshot is preserved at tag
`checkpoint/phase-4-lcd_ui-parked-2026-06-23`. A rebuild is planned post-Gateway.

## Build Instructions

**Host unit tests.** The firmware version header is generated first (CI does the same):

```bash
python3 scripts/gen-version.py firmware/shared/firmware_version.h.in firmware/shared/firmware_version.h
cd tests
ceedling test:all                                                  # Field Device and shared tests
CEEDLING_MAIN_PROJECT_FILE=project_gateway.yml ceedling test:all   # Gateway tests
```

The two Ceedling projects are separate because a Gateway module and a Field Device module can
share a file name. One module, with static analysis and formatting, from the repository root:

```bash
scripts/test-module.sh -m gw-<module>      # Ceedling + cppcheck + clang-format-17 (add -f to fix)
scripts/test-module.sh -m fd-<module>
```

**Firmware images.** Both targets are built with STM32CubeIDE (headless builds are used in CI).
The Gateway bootloader and the Slot-A image have their own scripts, `scripts/build-bootloader.sh`
and `scripts/build-slot-a.sh`. Flashing and bench procedures for each module are in the header
of its bring-up harness under `firmware/*/integration-tests/`.

## Development Methodology

This project follows a **V-Model** lifecycle with model-based design:

1. System Requirements Specification (SRS)
2. High-Level Design / System Architecture (HLD)
3. Low-Level Design / Detailed Design (LLD)
4. Implementation ← *current phase*
5. Unit Testing
6. Integration Testing
7. System Testing
